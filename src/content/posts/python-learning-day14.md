>
> 主线只有一句：**快慢不是感觉，是可以量出来的倍数；倍数的形状，就是复杂度的名字。** 本文不背大 O 表，只回答三个问题：同一个查询换容器差多少、插入位置差多少、规模翻倍时时间怎么长。

## 一、先把“快慢”变成倍数

计时只用 `time.perf_counter()`，不用墙上时间，也不看单次毫秒数：

```python
import time

def timed(fn):
    t0 = time.perf_counter()
    result = fn()
    return result, time.perf_counter() - t0
```

规则只有三条：

1. 同一台机器、同一份数据、同一轮里比较，跨轮只看方向和量级。
2. 只比**比值**，不比绝对毫秒；同一段代码两轮差 20% 很正常。
3. 只跑一轮就下结论，等于没测。

下面的数据来自多轮运行，能背的是“哪一列永远赢、倍数落在哪个量级”，不是某一个毫秒数。

## 二、`x in list` 和 `x in set`，差的是查找方式

10 万个元素，查 1000 次，元素一半命中、一半不命中：

```python
big_list = list(range(100_000))
big_set = set(big_list)

sum(1 for x in found if x in big_list)
sum(1 for x in found if x in big_set)
```

```
轮次    list        set         倍数
1       121.8 ms    0.168 ms    727x
2       122.9 ms    0.171 ms    717x
3       125.4 ms    0.165 ms    758x
```

命中数三轮都是 `1000 / 1000`：**换容器只换速度，不换答案**。这是优化旧代码时最重要的一条安全边界。

### 为什么差这么多

- `list` 是连续数组，`x in list` 只能从头比到命中或表尾。
- `set` / `dict` 是哈希表，先算 `hash(x)` 定位桶，再用 `==` 确认；平均只比常数个元素。

所以复杂度要分三种情况记：

| 操作 | 平均 | 最坏 | 说明 |
|---|---|---|---|
| `x in list` 命中 | O(n) | O(n) | 平均扫 n/2 个 |
| `x in list` 未命中 | O(n) | O(n) | 必须扫完 n 个 |
| `x in set` / `x in dict` | O(1) | O(n) | 最坏是全撞到同一个桶 |

未命中比命中更慢，实测约 **2.1 倍**：

```
查到   121.3 ms
查不到 249.4 ms
```

原因不神秘：命中平均走到一半就停，未命中每次都要走到底。

> [!TIP]
> 不要背“set 快 700 倍”。要背的是：**list 线性、set/dict 平均常数；常数随实现和数据变，方向不变。** 面试里说“set 是 O(1)”时，补一句“平均情况，最坏 O(n)”，比只背结论完整。

## 三、转成 set 不是免费的：12–14 次才回本

把 10 万元素转成 set 要花一次 O(n)：

```
建 10 万元素 set     1.5–1.7 ms
list 里查一次        123–125 µs
回本需要             12–14 次
```

所以“只要用 in 就无脑先转 set”是错的。只查一次时，直接 `x in big_list` 可能更快；查十几次以上，转换费才摊得回来；如果数据本来就该保持有序、可重复、可切片，转成 set 还会丢掉这些性质。

```python
# 只查一次：不值得转
if target in numbers:
    ...

# 同一个集合要反复查：转换一次，循环里用
seen = set(numbers)
for item in new_items:
    if item in seen:
        ...
```

最后这个写法还顺手修掉了一个常见 bug：在循环里写 `if item not in seen_list: seen_list.append(item)`，每次都在 list 上做线性扫描，整体退化成 O(n²)。

## 四、交集：`any+in` 和 `set&set` 不是一句“set 更快”

同一个问题有两种写法：

```python
any(x in big_list for x in small)
bool(set(big_list) & set(small))
```

本轮数据：

```
any+in   0.18–0.20 ms
set&set  1.66–1.82 ms
结果一致 True
```

在这个数据上，`any+in` 反而快了约 9–10 倍。原因不是“any 比 set 高级”，而是 **`small` 里有一个元素很早就在 `big_list` 里命中**，`any` 立刻短路；`set&set` 却要先把 10 万元素完整建成 set。

把条件推到极端，差距更清楚：`small` 只有一个元素，而且那个元素就在 `big_list` 最前面。

```
单元素在表头：any+in 16.7 µs | set&set 1.765 ms
```

差了约 106 倍。

结论要分两层：

- **渐近上**：`set&set` 是 O(len(a)+len(b)) 平均；`any+in` 最坏是 O(len(small)×len(big))。
- **实际上**：`any` 会短路，`set&set` 要先付建表费；数据小、命中早时，`any+in` 更快。

所以不要拿一个用例给容器判死刑。先问：数据多大、查几次、命中大概在什么位置、结果要不要去重。

> [!TIP]
> 如果同一个大集合要参与多次交集，把 `set(big_list)` 在循环外建一次；如果在循环里每次 `set(big_list)`，你测到的就是建表费，不是交集本身的费。

## 五、尾部加和头部加：`append` 与 `insert(0)`

同样 2 万次插入：

```python
def fill_append(n):
    a = []
    for i in range(n):
        a.append(i)
    return a

def fill_insert0(n):
    a = []
    for i in range(n):
        a.insert(0, i)
    return a
```

```
append       0.42–0.43 ms
insert(0,x)  42.42–42.62 ms
倍数         99–102x
内容一样？   False
第一个元素   0 / 19999
```

两个列表长度一样，但内容顺序相反：`append` 得到 `[0..19999]`，`insert(0)` 得到 `[19999..0]`。**“插入位置”本身就是语义的一部分**，不只是性能问题。

为什么 `insert(0)` 这么贵：每插一个元素，后面的元素都要整体后移一格。第 i 次要移 i 个，总共移动：

```text
0 + 1 + 2 + ... + (n-1) = n(n-1)/2
```

这是 O(n²)。20k 时实测约 100 倍而不是 20k 倍，是因为 `memmove` 是 C 层的连续内存操作，常数很小；规模再涨，差距还会继续拉大。

要头尾都能快速进出，用 `collections.deque`；要保留 list 的随机访问，可以用 `append` 加最终 `reverse()`，或者先收集再反转。

## 六、`deque`：头部快 75 倍，按下标慢 4 倍

```
头部灌 2 万个：deque.appendleft 0.55–0.57 ms | list.insert(0,x) 42.42 ms
倍数：75–78x
```

但 `deque` 不是 list 的全面替代品：

```
按下标取 1000 个：list 144 µs | deque 588–646 µs
deque 是 list 的约 4 倍慢
```

原因是 `deque` 用分块数组，按下标要先定位到块，再在块内走；list 是连续内存，`a[i]` 直接算地址。

选择标准：

- 只在两端进出、不需要随机访问：`deque`。
- 需要 `a[i]`、切片、排序、二分：`list`。
- 既要在头部插入又要随机访问：先问清楚哪个操作更多，再选；没有一种容器全赢。

## 七、规模翻倍时，看的是形状

同一段代码，把输入规模翻倍或放大 10 倍：

| 操作 | 规模变化 | 两轮耗时 | 倍数 | 形状 |
|---|---|---|---|---|
| `append` | 1 万 → 2 万 | 0.30→0.46 ms / 0.23→0.44 ms | 1.5–1.9x | 线性 |
| `insert(0)` | 1 万 → 2 万 | 10.62→42.12 ms / 11.03→41.98 ms | 3.8–4.0x | 平方 |
| `sorted` | 1 万 → 10 万 | 0.74→9.68 ms / 0.71→10.22 ms | 13.1–14.3x | n log n |

`append` 规模翻倍、时间约翻倍，这是线性；`insert(0)` 规模翻倍、时间约 4 倍，这是平方；`sorted` 规模 10 倍、时间 13–14 倍，正好落在 n log n 的区间里。

为什么 `sorted` 不是 10 倍（线性）也不是 100 倍（平方）？因为 n log n 里多了一个 log：

```text
10 万 / 1 万 = 10 倍规模
log2(10 万) / log2(1 万) ≈ 16.6 / 13.3 ≈ 1.25
10 × 1.25 ≈ 12.5 倍
```

实测 13–14 倍，和这个估算同向。排序比例会飘，飘在 12–15 倍都正常；如果量到 100 倍，才要怀疑代码写错了。

> [!TIP]
> 复杂度不是“考试名词”，是**规模翻倍时时间的增长形状**。你不需要记住每一行的精确倍数，但要知道：线性约 2 倍、平方约 4 倍、n log n 略高于线性。

## 八、hash 相等就会合并：`1`、`1.0`、`True`

```python
s = {1, 1.0, True}
d = {1: 'a', 1.0: 'b', True: 'c'}
```

```
set 长度 1 | 内容 {1}
dict 长度 1 | 内容 {1: 'c'}
hash(1) == hash(1.0) == hash(True)  True
1 == 1.0 == True                    True
```

三样东西哈希相等、`==` 也相等，所以在 set 里只留一个，在 dict 里只留最后一个值。`True` 是 `int` 的子类，`True == 1`；这不是 bug，是 Python 的数据模型。

这会咬人的场景：

- 同时把 `1` 和 `True` 放进同一个 set，再去重，长度是 1 不是 2。
- 用 `bool` 当 dict 的 key，`True` 和 `1` 会互相覆盖。
- 从 JSON 读出来的 `true` 和 `1`，在 Python 里可能被当成同一个键。

`in set` 的完整过程是“先 hash 定位，再 `==` 确认”。哈希碰撞多的时候，桶里会退化成链表/树，最坏 O(n)；平均 O(1) 的前提是哈希散得开。

## 九、什么能当 key：可变对象不行

```python
{[1, 2]: 'v'}        # TypeError: unhashable type: 'list'
{(1, 2): 'v'}        # 可以
{(1, [2]): 'v'}      # TypeError: unhashable type: 'list'
```

- `list` 可变，不能保证哈希值稳定，所以不可哈希。
- `tuple` 本身不可变，但如果里面装了 `list`，整体仍然不可哈希；元组的哈希需要每个元素都可哈希。
- 可变对象当 key 的坏事不是“hash 会变”，而是**你改完对象后，用原来的内容再也找不到那个桶**；字典不会自动搬家。

自定义类要注意：写了 `__eq__` 不写 `__hash__`，Python 会把类标成不可哈希，`set` 里放不进去，报错还很费解。要么两个一起写，要么用 `@dataclass(frozen=True)`。

## 十、`sorted(key=...)` 的 key 只调用 n 次

```python
calls = 0

def slow_key(x):
    global calls
    calls += 1
    return -x

sorted(data_10k, key=slow_key)
print(calls)
```

```
1 万元素：key 调用 10,000 次
10 万元素：key 调用 100,000 次
```

不是 n log n，是 n。`sorted` 在排序前先对每个元素算一次 key，把 `(key, value)` 存下来，之后只比较 key；这就是 decorate-sort-undecorate。

所以：

- 一次 `sorted(key=...)` 不会因为比较次数多而重复调用 key。
- 如果 key 很贵，而且你排序后还要用这个 key，或者要对同一批数据排多次，可以自己先算成 `(key, value)` 再复用。
- `max`、`min` 带 key 时也是一次遍历、每个元素算一次 key。

> [!TIP]
> 看到“排序里 key 被调用 n log n 次”这种说法，可以直接纠正：**一次排序是 n 次 key 调用**；n log n 说的是比较次数/时间形状，不是 key 的调用次数。

## 十一、一页速查

| 操作 | `list` | `set` | `dict` | `deque` |
|---|---|---|---|---|
| `x in` | O(n) | O(1) 平均，O(n) 最坏 | O(1) 平均，O(n) 最坏 | O(n) |
| `a[i]` / `d[k]` | O(1) | 无下标 | 按键访问 | O(n) |
| 尾部追加 | O(1) 摊销 | — | — | O(1) |
| 头部插入 | O(n) | — | — | O(1) |
| 排序 | O(n log n) | — | — | — |
| 保持顺序 | 是 | 否 | 是（3.7+ 插入顺序） | 是 |
| 允许重复 | 是 | 否 | 键不重复 | 是 |

`dict` 和 `set` 都靠哈希定位，但顺序性质不同：`dict` 从 3.7 起保留插入顺序，`set` 不保留。别把两者混成一句“哈希容器都没有顺序”。

选择标准，按优先级问：

1. 需要按位置访问、切片、排序吗？需要就 `list`。
2. 主要是“在不在”“出现几次”“去重”吗？是就 `set` / `dict`。
3. 只在两端进出、不需要随机访问吗？是就 `deque`。
4. 数据小、只查一次，别为了“更高级的容器”付建表费。

## 十二、面试里被问“这段代码慢在哪”，怎么答

一个可复用的五步：

1. **先问规模**：数据多大、查询多少次、命中多不多。
2. **找热点操作**：是成员查询、头部插入、排序，还是嵌套循环。
3. **说容器**：list 连续扫描、set/dict 哈希定位、deque 分块两端操作。
4. **给复杂度和常数**：平均 O(1) 不是免费，建表要 O(n)；O(n²) 的常数可能很小，但规模一大就现形。
5. **给替代方案和代价**：换 set 会丢顺序，换 deque 会丢随机访问，换 dict 会多占内存。

两个常见例子：

```python
# 例 1：循环里用 list 做 seen
seen = []
for x in new_items:
    if x not in seen:
        seen.append(x)
# 最坏 O(n²)；改成 set(seen) 后平均 O(n)，但会丢掉插入顺序
```

```python
# 例 2：头部插入
for x in items:
    result.insert(0, x)
# O(n²)；改成 append + reverse，或 deque.appendleft
```

回答时别只说“set 更快”。补上“平均 O(1)、最坏 O(n)、建表 O(n)、无序、不能放可变对象”，才算把容器讲完整。

## 十三、可带走的问题清单

1. 10 万元素里只查 1 次，`list` 和 `set` 谁快？为什么？
2. 同一个 list，查不到为什么比查到慢？大概慢多少？
3. `insert(0)` 2 万次为什么不是 2 万倍慢？它的总移动量是什么形状？
4. `deque` 头部快，但什么时候不该用它？
5. `1`、`1.0`、`True` 同时放进 set，长度是多少？为什么？
6. `(1, 2)` 能当 key，`(1, [2])` 为什么不能？
7. `sorted(key=...)` 对 10 万元素调用 key 几次？不是 n log n 吗？
8. 你正在写的代码里，有没有在循环里做 `x in list`？数据规模多大？能不能一次转成 set？

## 十四、小结

- `list` 快在连续内存和按下标访问，慢在线性扫描和头部插入。
- `set` / `dict` 快在哈希定位，代价是建表、内存、`set` 无序、可变对象不能当 key；`dict` 从 3.7 起保留插入顺序。
- `deque` 快在两端，慢在按下标访问。
- 复杂度是形状，不是某一次的毫秒数；同机多轮、只看比值，才不会被计时噪声骗。
- 优化的第一步不是换容器，是**先确认热点操作和数据规模**。
