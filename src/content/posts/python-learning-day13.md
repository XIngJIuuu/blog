> [!NOTE]
> 这是第十三天 Python 学习笔记，形式延续前几篇：**按条目排的可查清单**，每条结论下面都跟着这台机器上跑出来的实测输出（CPython 3.11.9）。
>
> Day 9 讲生成器时立过三条硬代价：**只能消耗一次、错误被推到第一次取值、没有 `len` 和下标**。今天不重复那套论证，只做一件事——把同样的三条按在 `map` 和 `filter` 身上，看它们是不是一条都不差。结论先给：**`map` / `filter` 返回的根本不是"结果"，是一张还没执行的配方。**

## 一、主线：它返回的不是数据，是"还没执行的计算"

```python
m = map(str, [1, 2, 3])
```

这一行执行完，`str` **一次都没被调用**。`m` 里面只装着三样东西：源可迭代对象的引用、函数本身、游标走到哪了。整篇的每个现象——为什么第二口是空的、为什么屏幕要等到 `list()` 那一刻才打字、为什么报错的行号不是写错的那一行、为什么它占 48 字节——全是这一句话的推论。

## 二、只能取一口

```python
m = map(str, [1, 2, 3])
print(list(m))
print(list(m))
```

```
① 第一口: ['1', '2', '3'] | type: map
① 第二口: []
```

第二口是**空的**，而且不报错。`list(m)` 把游标一路推到 `StopIteration`，推完就到头了，没有倒带这回事。`filter`、`zip`、`enumerate`、生成器全都一样。

对立面是推导式：`[str(x) for x in nums]` 产出一个 list，元素**真的在内存里**，所以能反复遍历、能下标、能排第二遍。

> [!TIP]
> 这就是 Day 9 那张表里"能用几次"那一行的第三次复现。生成器、`map`、`filter` 是同一族：**它们的返回值不可再生，list 才是可再生的。**

## 三、它不是列表：下标、`len`、`reversed` 三条全拒

```python
mo = map(str, ['b', 'a', 'c'])
mo[0]
len(mo)
reversed(mo)
```

三条 `TypeError` 原文：

```
② 下标 TypeError: 'map' object is not subscriptable
② len TypeError: object of type 'map' has no len()
② reversed TypeError: 'map' object is not reversible
```

三条都只点名 `map`，没有一句提到"里面有什么"。想拿第一个元素，最短的写法是 `next(mo)`——**它不需要先转成列表**。这一点值得单独实测，因为直觉正好相反：

```python
calls = []
def f(x):
    calls.append(x)
    return str(x)

big = map(f, range(1000000))   # 源是一百万个
print(next(big))
print(len(calls))
```

```
   next() 返回 0 | f 被调用次数: 1
   再来两次: 1 2 | 调用次数: 3
```

**一百万个元素的源，取第一个只调用了一次函数。** 后面九十九万九千九百九十九个此刻仍然不存在。真正"先转列表再取索引"的写法是 `list(big)[0]`——那才是把一百万个全算出来、然后只拿走一个。

顺带一条：`iter(big) is big` 实测为 `True`。`map` 对象本身就是迭代器，套一层 `iter()` 是白写。

## 四、`filter(None, xs)` 删的是假值，不是 `None`

```python
mix = [0, 1, '', 'a', None, [], [0], False, True]
print(list(filter(None, mix)))
```

```
③ filter(None, mix): [1, 'a', [0], True]
```

`0`、`''`、`None`、`[]`、`False` 全被删了。注意 **`[0]` 留着**——非空列表是真值，哪怕里面装的是 `0`。

官方中文文档在 `filter` 那一条里写得很直接（原话照抄）：*"如果 function 为 None，则会使用标识号函数，也就是说，iterable 中所有具有假值的元素都将被移除。"* 这个中译里的"**标识号函数**"就是英文原文的 `identity function`，说人话是**恒等函数**：原样返回、什么都不做。所以写 `None` 不是"不筛"，而是"**拿元素自己去当条件**"。

想只删 `None`、留下 `0` 和空串，得自己说清楚：

```python
list(filter(lambda x: x is not None, mix))     # 或者 [x for x in mix if x is not None]
```

## 五、空 `map` 放进 `if` 里，永远为真

```python
print(bool(map(str, [])), bool(filter(None, [])))
if map(int, ['x']):
    print('这个 if 进去了')
```

```
④ bool(空map): True | bool(空filter): True
④ 这个 if 进去了
```

一个**装不出任何元素**的 `map` 对象，布尔值是真。原因是它既没有 `__bool__` 也没有 `__len__`——`len(mo)` 当场报 `TypeError` 就是第三节的证据。缺了这两个钩子，Python 对任何对象都只能按"真"处理。

所以 `if map(f, xs):` 这种写法**永远成立**，和 `xs` 空不空一点关系都没有。想表达"有数据才处理"，要么先落成 list（`xs = list(map(f, src))` 再 `if xs:`），要么用 `next(it, None) is not None`——**但后者会吃掉第一个元素**。这条是真会在生产里咬人的：空数据的分支永远走不到，读代码的人完全想不出为什么。

## 六、副作用发生在消费那一刻

```python
def touch(x):
    print('   touch 跑了:', x)
    return x * 2

plan = map(touch, [1, 2, 3])
print('⑤ 上面那行 map(...) 有没有打印东西')
print('⑤ 现在还没消费，屏幕上 touch 跑了几次')
list(plan)
```

实际屏幕输出，一个字都不差：

```
⑤ 上面那行 map(...) 有没有打印东西
⑤ 现在还没消费，屏幕上 touch 跑了几次
   touch 跑了: 1
   touch 跑了: 2
   touch 跑了: 3
```

`plan = map(...)` 这一行什么都没干，三行 `touch` 是 `list(plan)` 那一刻才打的。**"写了一行代码"和"这件事发生了"之间隔着一整个惰性。**

`open()` 你是记得"不读就不算打开"的，`map` 就忘了——同一个道理。写测试时这条最坑：`assert map(f, xs) is not None` 永远通过，但它一次都没真的跑过。

官方文档在 `zip` 那一条里把这件事说得比谁都白：*"zip() 是延迟执行的：直至迭代时才会对元素进行处理，比如 for 循环或放入 list 中。"* `map` / `filter` / `zip` 是一族，这一句三个都管。

## 七、异常抛在消费那一行，不在出错那一行

这一条是前面所有推论里最贵的一条，因为它直接决定你查 bug 要花多久。

```python
bad = ['1', '2', 'x', '4']
print('⑥ 先创建 map，不消费:')
try:
    lazy = map(int, bad)    # 数据在这一行进来，什么也没发生
    print('   创建这一行没报错')
    print('   消费:', list(lazy))   # 炸在这一行
except ValueError as e:
    print('   ValueError:', e)
```

```
⑥ 先创建 map，不消费:
   创建这一行没报错
   ValueError: invalid literal for int() with base 10: 'x'
```

第二行 `消费:` 压根没打印出来：异常发生在 `list(lazy)` 求值的过程中，那句 `print` 连执行都没轮到，`lazy` 也在这一步被消耗到中断。

把这两段写成真实文件、用 `traceback.extract_tb` 打印指向的行号（下面的数字就是那个文件里的真实行号）：

```python
CODE = ['1', '2', 'x', '4']

lazy = map(int, CODE)      # 第 4 行
try:
    list(lazy)             # 第 6 行
except ValueError:
    print(traceback.extract_tb(sys.exc_info()[2])[-1].lineno)
```

```
map 版 traceback 指向行号: 6    ← 而 map(...) 的创建行是第 4 行
推导式 traceback 指向行号: 11   ← [int(x) for x in CODE] 就在第 11 行
```

**`map` 版的报错指向消费那一行，创建那一行不留任何痕迹；推导式版写在哪行就在哪行炸**（它当场把整表算完），而且因为异常出在赋值右侧，结果变量压根没被绑定——实测 `'r' in dir()` 是 `False`。

再想一层：如果 `map` 在 A 函数里创建、在五百行外的循环里消费，traceback 会指向那个循环，报错信息里只有一个 `'x'`，**没有任何线索告诉你这批数据是从哪儿读进来的**。这就是"惰性"在调试上的账单。

## 八、长度不等，多的那截静默消失

```python
list(map(lambda a, b: a + b, [1, 2, 3], [10, 20]))
```

```
⑦ 两个长度不等的 map: [11, 22]
```

`3` 没了，**没有任何提示**。官方文档给这个行为背书的句子是：*"当有多个可迭代对象时，当最短的可迭代对象耗尽则整个迭代将会停止。"* `zip` 同规则。

`zip` 那一条里，官方把长度不等列成三种方案，措辞值得逐字看：

| 方案 | 行为 | 官方用的词 |
|---|---|---|
| 默认 | 最短的用完就停 | 较长可迭代对象中剩余的项**将被忽略** |
| `zip(..., strict=True)` | 长度不齐立刻 `ValueError` | 推荐用于"本该等长"的场合 |
| `itertools.zip_longest(..., fillvalue=…)` | 补齐到最长 | 让所有可迭代对象变等长 |

而且官方直接写了这句：**"如果未指定 strict=True 参数，所有导致可迭代对象长度不同的错误都会被抑制，这可能会在程序的其他地方表现为难以发现的错误。"** ——抑制，不是忽略。

配套的实测：

```
⑦ zip_longest 版: [(1, 10), (2, 20), (3, 0)]
zip(..., strict=True) → ValueError: zip() argument 2 is shorter than argument 1
```

注意 `zip_longest` 吐的是**元组的列表**，不是相加后的结果；要相加得再来一层：`[a + b for a, b in zip_longest(...)]` → `[11, 22, 3]`。

> [!TIP]
> 这和 Day 12 第十一节"元组里混类型有时不报错"是**同一类问题的第二种隐身法**：昨天靠"主键恰好不重复"，今天靠"长度恰好不等"。共同点是**该报的错在特定数据上不来**，于是你以后以为它永远不会来。

## 九、版本这条线：`zip` 有 `strict`，`map` 没有

想给 `map` 也加个保护：

```python
list(map(str, [1], strict=True))
```

```
⑩ TypeError: map() takes no keyword arguments
```

它报的不是"没有 `strict` 这个参数"，而是"**不接受任何关键字参数**"——连参数名都没查就拒了。原因在函数签名：

| 版本 | `map` 的签名 | `zip` 的 `strict` |
|---|---|---|
| 3.11（本机） | `map(function, iterable, *iterables)` | **有**（3.10 加的） |
| 3.14（最新文档） | `map(function, iterable, /, *iterables, strict=False)` | 有 |

`/` 的意思是"它左边的参数只能按位置传"。而 3.11 的 `map` 连 `*` 后面那一截都还不存在。

**同一个参数名，`zip` 吃、`map` 不吃，连报错类型都不一样**（`ValueError` 对 `TypeError`）。所以"要求长度对齐"这件事今天就能写：

```python
list(map(sum, zip(a, b, strict=True)))     # 实测：长度不齐时抛 ValueError
```

这条的真正用途不是这个技巧，是一个习惯：**看文档先看右上角的版本号，让它和你本机 `python -V` 对上再抄。**

## 十、`Counter` 的三种"减法"回答三个不同问题

这一条是从力扣 242（有效的字母异位词）长出来的。三份实测：

```python
c1, c2 = Counter('ab'), Counter('aabb')
c1 - c2                    # ①
c1 == c2                   # ②
c1.subtract(c2)            # ③（c1 被原地改掉）
```

```
⑧ c1-c2: Counter()          c1==c2: False      c1 减法后仍是: {'a': 1, 'b': 1}
   c2-c1: Counter({'a': 1, 'b': 1})
   c3.subtract(c2) 之后: {'a': -1, 'b': -1}
```

三行分别说明三件事：

| 写法 | 回答的问题 | 关键点 |
|---|---|---|
| `c1 - c2` | 左边**多出**哪些 | 结果 ≤ 0 的键**被整个删掉**，不留 0 也不留负数；**不改动任何一方**，返回新对象 |
| `c1 == c2` | 两边**是否相同** | 判异位词只能用这个 |
| `c1.subtract(c2)` | 左边**缺**哪些 | **真的原地改**，而且**把 0 和负数都留着** |

最容易踩的是第一条：既然"不够的键被删掉了"，那 `c1 - c2` 为空就只能说明**左边没有任何一格超过右边**——也就是"左边是右边的子多重集"。`Counter('ab') - Counter('aabb')` 是空的，可 `'ab'` 和 `'aabb'` 明显不是异位词，长度都不等。**"相减为空"离"两者相等"差着一整个"是不是子集"。**

顺带把上一条笔记里那句订正补在这里：`reverse=True` **不会**让等键元素倒序（官方：*reverse 参数仍然保持排序稳定性*），它翻的是比较方向。这三个 `Counter` 操作和那条是同一个教训——**运算符名字给你的直觉，常常和它实际干的事差一步。**

## 十一、什么时候还是该用 `map`

前面十条都在数落 `map`，但社区那条"推导式优先"的规矩，理由**不是速度**。先看实测（本机 3.11.9，表长 1000，各跑两万次，连测五轮）：

| 轮次 | `list(map(str, nums))` | `[str(x) for x in nums]` | 推导式快 |
|---|---|---|---|
| 1 | 1.0199s | 0.9218s | +9.6% |
| 2 | 1.2324s | 1.0918s | +11.4% |
| 3 | 1.2509s | 1.0927s | +12.7% |
| 4 | 1.2622s | 0.9818s | +22.2% |
| 5 | 1.1307s | 0.9799s | +13.3% |

内置函数 `str` 当参数时，**这五轮全是推导式赢**。今天还为这件事跑过另外两批：一次五连测（推导式也是 5 战 5 胜）、两次单跑（`0.8240 vs 0.6794`、`1.0652 vs 0.7459`）。**加起来 12 次对照，内置函数那一组推导式 12 次全赢。** 而换成自己写的函数：

```
R1 自定义: map 1.3798 | 推导式 1.5538   推导式慢 12.6%
R2 自定义: map 1.6414 | 推导式 1.5297   推导式快  6.8%
R3 自定义: map 1.6958 | 推导式 1.5592   推导式快  8.1%
R4 自定义: map 1.4706 | 推导式 1.5955   推导式慢  8.5%
R5 自定义: map 1.4359 | 推导式 1.5496   推导式慢  7.9%
```

五轮里推导式赢两轮、输三轮，幅度 7%~13% 之间来回跳。**"map 更快"这句常识，对内置函数是错的，对自定义函数是不可靠的。**

再看绝对值：同一段代码、同一台机器，今天这几个小时里 `list(map(str, nums))` 最快跑出 `0.8240s`、最慢跑出 `1.9631s`，**差了 2.4 倍**。**timeit 的绝对值连量级都不稳，百分比只有多轮同向才勉强算结论。**

那 `map` 凭什么活着？凭这一句：`list(map(str.strip, lines))` **不用给中间变量取名**，一眼看出"整张表做同一个操作、不改形状"。一旦要筛选、要改形状、要写表达式，推导式更清楚。官方的态度也在这边——`filter` 那一条紧接着给了等价式（原话：*"请注意，filter(function, iterable) 相当于一个生成器表达式……"*）：

```
filter(function, iterable)  ≡  (item for item in iterable if function(item))
filter(None, iterable)      ≡  (item for item in iterable if item)
```

**官方自己拿生成器表达式来解释 `filter`。** 实测两边输出完全一致：

```
   filter(奇数): [1, 3, 5]  | 推导式: [1, 3, 5]
   filter(None): [1, 2]     | 推导式: [1, 2]
   map(str.strip): ['a', 'b'] | 推导式: ['a', 'b']
```

还有一条值得单独拎出来的用法：`sum` / `max` / `any` / `all` 这些**终结函数直接吃惰性对象**，中间那个列表根本不用存在。

```python
sum(len(w) for w in words)      # 5
sum(map(len, words))            # 5，两种都不建中间列表
```

## 十二、48 字节"装着"一千个字符串

```python
print(sys.getsizeof(list(map(str, range(1000)))))
print(sys.getsizeof(map(str, range(1000))))
```

```
⑩ list 的 getsizeof: 8856 | map 的 getsizeof: 48
```

`map` 里只有"函数 + 源的引用 + 游标"，那一千个字符串**此刻一个都不存在**。`list(map(...))` 之后它们才被创建出来，容器要装一千个指针，所以 8856。

而 `8856` 这个数在 **Day 9 那张表里出现过**：当时量的是 `n=1000` 的列表（生成器 208 / 列表 8856）。同一个容器大小，因为 `getsizeof` 量的只是**容器外壳**，不含里面装的对象。

所以"48 字节表示一千个字符串"不矛盾：那 48 字节表示的是**一千次还没执行的计算**。

## 十三、力扣 136：只出现一次的数字

今天写的是**计数版**——用一个 dict 当计数器，第二趟找计数为 1 的键。

```python
class Solution:
    def singleNumber(self, nums: List[int]) -> int:
        counter = {}
        for i in nums:
            counter[i] = counter.get(i, 0) + 1
        for key, value in counter.items():
            if value == 1:
                return key
```

实测：

```
[2, 2, 1]        -> 1
[4, 1, 2, 1, 2]  -> 4
[1]              -> 1
[7, -3, -3, 9, 7] -> 9      负数能过
[0, 0, 5]        -> 5        答案是 5，不是 0
[1, 1]           -> None     ← 没有解时隐式返回 None
{4: 1, 1: 2, 2: 2}           计数 dict 的键顺序 = 首次出现顺序
```

力扣的输入保证一定有解，所以判题能过；**但"函数有一条路径不返回值、隐式返回 `None`"这件事是真实存在的**，和 Day 12 那道 LC26 在空数组上返回 `1` 是同一种"判题能过 ≠ 函数正确"。

另一解是一行的异或：`a ^ a == 0`、`0 ^ b == b`，加上异或满足交换律和结合律，所以数组顺序根本不重要，成对的自己抵消。

```
[1, 1] 计数版 -> None    异或版 -> 0
```

**两版连"无解"这个行为都不一样。** 而更值得记的是代价：计数版要一个 O(n) 的字典，异或版只要一个变量——**同一道题，额外空间差一个 n。** 这正是明天要正面对算的东西。

## 十五、小结

整篇一句话：**`map` / `filter` 返回的不是结果，是一张还没执行的配方。**

- 因为配方不存成品，所以**只能照着一口**（第二、三节）。
- 因为还没执行，所以**副作用推迟**到消费那一刻（第六节），**异常也推迟**到那一行（第七节）。
- 因为配方不存成品，所以它**不能下标、没有长度、布尔值永远是真**（第三、五节）——它看起来像个容器，其实只是个"待办"。
- 因为配方要走到头才知道有没有下一步，所以**最短的那条路走完了就收工**，多出来的静默消失（第八节）。
- 因为省下了中间成品，它才只占 48 字节（第十二节）；但**省内存不等于更快**，实测计时连方向都不稳（第十一节）。

Day 9 问的是"这个对象能被取几次"，Day 10 问的是"这次改动落在原对象上还是只挪了名字"，Day 12 问的是"到底是谁在比大小"。这篇问的是：**这一行代码，究竟在什么时候真的发生了事情。** 五个问题的共同点是同一个：**Python 里很多看起来"已经做完"的表达式，其实只是把要做的事记了下来。**
